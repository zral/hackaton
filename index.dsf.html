01 · Bakgrunn

Hva er en Dark Software Factory?

Mennesket definerer hva og hvorfor. Orkestratoren koordinerer. Agentene produserer. Fabrikken er mørk — ingen trenger å være til stede.

🧠

Mennesket gir intent

Én løs setning. Agentene skriver plan, scenarioer, kode, review og analyse — alt. Det er det eneste mennesket leverer.

~ 1 setning
🤖

Agentpipeline

Arkitekt → Utvikler → Review + Test (parallelt) → Eval → Commit. Hvert steg blokkeres av hooks om kvalitetsporten ikke passerer.

5 agentroller
🔒

Holdout-barriere

Fasiten skrives FØR koden starter. Eval-agenten ser aldri koden — bare API + scenarioer. Blokkerer ved < 80% satisfaction.

train/test split
🔄

Selvevolverende

Hvert review-funn → ny regel i SKILL.md → neste agent unngår feilen automatisk. Fabrikken blir smartere for hvert kjør.

continuous improvement

02 · Prinsipper

Fem byggeklosser

Hele fabrikken hviler på fem prinsipper. Fjern én — og kvalitetsgarantien ryker.

Prinsipp 01

CLAUDE.md — Kontrakten

Brifingen til en senior utvikler som starter dag én. Bedre CLAUDE.md → bedre output.

## Compliance-regler
RegelStatusKort versjon
amount_threshold Flagged > 100 000 NOK
sanctioned_country Rejected KP / IR / SY / CU / RU
pep_check PendingReview PEP + > 50k NOK
## Etablerte beslutninger (ikke til diskusjon)
  • Beløp alltid long (øre) — aldri decimal
  • 200 OK for screening — ikke 201
  • IScreeningRule er kontrakten
## Ikke-forhandlbare regler
  • ALDRI implementer uten plan
  • ALDRI la orkestrøren skrive kode
  • ALLTID kjør review og test parallelt
💡 Å forbedre CLAUDE.md er det høyest-verdiskaping et menneske gjør. Det er fabrikkens instruksjonsmanual.

10 review-funn — alle fanget FØR holdout

Review-agenten fant kritiske feil. Utvikler-agenten fikset dem. Slik er det ment å fungere.

  • F3 HIGH Ingen input-validering på POST — negative verdier og nullverdier passerte gjennom
  • F1 MOD Mutable string[] i sanksjonert landliste
  • F2 MOD Ingen landkodevalidering på regelnivå
  • F3 LOW Død null-guard — ureachable etter filter ble lagt til
  • F2 LOW UTC midnight race — to uavhengige UtcNow-kall
  • F4 INFO FakeDailyLimitStore manglet AddCallCount — dårlig testkvalitet
🔍 Dyreste: F3 validering — 2 QC-runder. Rotårsak: Minimal API ignorerer [Required] på records. → Lagt til developer/SKILL.md etter kjøret. Neste syklus: dette problemet eksisterer ikke.

04 · Workshop

Tre spor — én pipeline

~55 min · Repo delt av fasilitator · claude --dangerously-skip-permissions

Track 1 — Grunnleggende

🟢 AI legger til regelen for deg

Følg med gjennom alle faser. Kopier prompten direkte. Se fabrikken i aksjon.

~45 min
  • Kopier den ferdige prompten direkte fra doc/workshop-tasks.md
  • Følg med gjennom alle faser: Plan → Impl → QC → Holdout → Commit
  • Oppgave: legg til currency_restriction-regelen
  • Alternativ: duplicate transaction check
Legg til currency_restriction-regelen til compliance-servicen. Regelen: Flagged ved transaksjoner i BTC, ETH eller XMR. Beløpsgrense: long (øre) · følg DSF-protokollen.
Track 2 — Avansert

🟡 Du spesifiserer — AI leverer

Skriv din egen regelspesifikasjon. Se hva som skjer med vag vs. presis spec.

~55 min
  • Skriv din egen regelspesifikasjon — fri tekst
  • Eksperimenter: vag spec vs. presis spec — hva er forskjellen i output?
  • Forslag: geo_risk_flag eller round_amount_flag
  • Bonus: CI-feil og self-healing (se neste lysbilde)
💡 Vag spec → agent tolker → kan gå galt. Presis spec → bedre output. Erfaring med hva som kan gå galt kreves for å skrive god CLAUDE.md.
Track 3 — Factory

🟣 Skriv fasiten først

Det ekte DSF-prinsippet: holdout-scenario committed FØR koden starter.

~55 min
  • Skriv holdout-scenario manuelt (se doc/workshop-tasks.md)
  • Commit scenario FØR implementasjon — dette er ordenen, og den er obligatorisk
  • Kjør eval-agent mot kjørende API
  • Bonus: endre en skill, kjør ny regel, se om fabrikken lærer
# Et holdout-scenario ser slik ut: ## Scenario: Valuta-restriksjon utløst **Request:** POST /api/v1/screen { "amount": 50000, "currency": "BTC", ... } **Expected status:** Flagged **Active rule:** currency_restriction **Rationale:** BTC er listet som restriktert valuta

🔴 CI feiler — det er forventet

CI-feil er input til dev-agenten, ikke en stoppesituasjon. Slik håndterer du det:

# Sjekk CI-status gh run list --limit 5 # Hent feildetaljer gh run view --log-failed # Send til dev-agenten: "CI feiler på branch main. Output: [lim inn output]. Analyser og fiks." # Etter fiks: git push gh run watch

05 · Diskusjon

Hva skjer med oss?

Fabrikken koder. Men hvem forstår hva koden gjør? Og hvem eier feilen når den når produksjon?

01

Utviklerrollen

Fra å skrive kode til å skrive CLAUDE.md. Fra implementasjon til intent. Er det en ny type seniorrolle — domenekspert med nok teknisk forståelse til å evaluere fabrikken?

02

Junior-opplæring

Tradisjonelt: skriv kode → få review → forstå feil → bygg intuisjon. Når agenten skriver koden — hva skjer med læringsarenaen? Kan man lære debugging uten å ha skrevet mye kode?

03

Accountability

Koden er agentgenerert. Reviewen er agentgenerert. Hvem eier feilen når den når produksjon? DORA og Solvency II krever at finansinstitusjoner kan forklare og auditere all produksjonskode.

04

Teknisk gjeld og forståelse

Agenten genererer kode raskt. Men kjenner noen på teamet til hva som faktisk er i produksjon? Kan vi refaktorere uten å forstå det vi refaktorerer?

05

Kontroll vs. hastighet

Fabrikken kan produsere 1 000 linjer på 20 minutter. Gir det for lite tid til å forstå hva som leveres? Speed hides errors. More output ≠ more correct output.

06

Sikkerhet og avhengigheter

Agenten introduserer NuGet-pakker og setter opp Docker. Hvem gjør dependency review? Hvem oppdager sikkerhetssårbarheter i agentgenererte tredjepartspakker?

Diskusjonsspørsmål

  1. Hva overrasket deg mest under workshopen — positivt eller negativt?
  2. Hvilke oppgaver i teamet ligner mest på det fabrikken løser?
  3. DORA / Solvency II — er agentgenerert kode forsvarlig i en regulert virksomhet?

Om tid: Hva måtte du spesifisere mer presist enn forventet? · Kan juniorer lære å kode godt uten å skrive kode? · Hva er den viktigste ferdigheten en senior trenger i DSF? · Hvor vil du sette inn human review i en reell pipeline?

💡 Tips

Fra fabrikkmesteren

Praktisk visdom fra dem som har kjørt fabrikken — og sett hva som går galt.

📄

CLAUDE.md er høyest-verdiskapende arbeid

Tid brukt på å forbedre CLAUDE.md er bedre investert enn tid brukt på å fikse agent-output. Presis tekst → bedre fabrikk.

🔐

Commit holdout-scenariet FØR du starter agenten

Rekkefølgen er obligatorisk. Scenario committed → dev-agent starter. Ikke omvendt. Ellers er det ikke holdout — det er bare en navngitt test.

⚡

Start enkelt, evaluer, iterer

En presis spec for én regel > en vag spec for fem regler. Fabrikken skalerer når du stoler på protokollen — ikke før.

🔍

Hooks er ikke byråkrati — de er fabrikken

Fristelsen er å bypass hooks når de blokkerer. Det er feil. Hookens blokkering er informasjon: protokollen er brutt, og det er det som skal fikses.

📊

Les analyse-rapporten etter hvert kjør

doc/*-analyse.md skrives automatisk. Den inneholder: timing, review-funn, test-analyse, og prosessforbedringer. Det er herfra skills-oppdateringer kommer.

🤔

Det viktigste spørsmålet er ikke «kan AI skrive kode?»

Det kan. Spørsmålet er hva som er igjen for oss — og hva vi vil gjøre med det.
